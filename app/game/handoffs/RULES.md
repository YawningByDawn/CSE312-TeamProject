# Rules for every builder (read first, every time)

1. Read `CLAUDE.md`. The binding design is `DECISIONS.md` (§13 overrides anything earlier that conflicts). Your piece's brief is `handoffs/briefs/<piece>.md`; your running log is the handoff file named there.
2. **You may be stopped at any moment** (it has happened several times). After every milestone, update your handoff file: done / in progress / files touched / exact next steps / requests. A successor continues from that file and the code on disk. If you are a successor: read the handoff, check the files on disk (the previous builder may have been stopped mid-edit — run `npx tsc --noEmit` first and repair your own files), then continue; do not restart finished work.
3. **Never run git.** The orchestrator commits and pushes.
4. **Ownership:** edit only the files your brief says you own. Many builders work at once; files you do not own may be transiently broken — wait and retry, never fix them. Requests to another owner go into your handoff file under "Requests" (or the shared request file your brief names), exact and small. Public APIs change additively only.
5. **Owner's hard rules:** Void is exact `#000`. No visible band, rim, lip, halo or glow at any fog or rock boundary; no straight or stepped fog/terrain edges. Nothing floats over heads; no labels in the world. Plain names (DECISIONS §13.3). All terrain art follows `handoffs/ART-REFERENCE.md` (crops in `handoffs/ref/`); the only benchmark is `docs/refs/mine.png`. It is a slice: late-game balance is not a goal (§13.7).
6. **Tools:** Playwright is global — `NODE_PATH=/usr/local/lib/node_modules_global`, helpers in `e2e/lib/browser.cjs` (`launch`, `startServer(port)`, `collectConsole`); never run `playwright install`. Use only your own port (in your brief). Block or stub Vite's HMR websocket in scripts (other builders' edits trigger reloads), or measure on a static build in your scratch dir. Scratch files go under `/tmp/<piece>/`, not the repo.
7. **Measuring:** the machine is a shared 4-core, software-rendered box under heavy load. Take medians of several runs, state `uptime` load with each number, compare against a blank-canvas control when judging frame time, and measure delivered cost (forced flush / rAF interval), not just JS time.
8. **Context discipline (hard):** never Read a full-size screenshot — downscale to ≤ 800 px wide or crop first; at most ~40 image reads; prefer numeric pixel checks. Report well before 350k tokens of context.
9. **Before reporting:** `npx tsc --noEmit` clean for your files; relevant `npx vitest run` green; zero console errors/warnings on your pages; no runtime network fetches; external libraries only if the licence permits, recorded in `CREDITS.md`; append your round's note to your section of `DECISIONS.md`.
10. **Final message:** what changed; per work item fixed / partly / not with measured numbers and evidence paths; API additions; requests to other owners; known issues; what a critic would still fault.
11. **Browser runs are serialised:** the machine has 4 cores and about twenty builders. Wrap every Playwright/Chromium run in a lock chosen by your port: `flock /tmp/hg-pw-$((PORT % 3)).lock node <script>` (so at most three browsers run at once). Keep runs short; close the browser; never leave a watch-mode test, a second dev server or a background bake running. Type-check only your own files where you can (`npx tsc --noEmit` output filtered to your paths).
12. **Interface first:** if another piece will call yours, put the exact public interface (functions, types, names) at the top of your handoff within your first ten tool calls, before implementing, and change it additively only. If you call another piece, do it through one thin adapter file of your own and use a small local stand-in until the real thing exists — never wait idle for another builder.
13. **Grade yourself (owner's rule, 2026-11-23: "have them grade themselves; a blind critic only before it is the owner's/orchestrator's turn"):** you are your own first critic. After every milestone produce the real evidence (screenshots / frame strips / test and bot output / measurements), look at it downscaled next to the reference or the requirement, and write in your handoff under "Self-grade": a score out of 10 against the bar "a shipped indie game", the three worst things a hostile critic would say, and what you will do about them. **Do not report as finished below an honest 8** — keep iterating (there is no round limit). Inflated self-grades are found out: a blind critic judges the integrated build before it reaches the owner, and the orchestrator looks at your evidence when you report. If you are stuck below 8, report early with the evidence and what blocks you.
14. **Do not burn a context on work nobody can use (owner: "you're wasting tokens"):** work in milestones that each end in a state that compiles and runs. Never begin a rewrite of a core file after ~200k tokens of context. At ~250k, stop at the next working state, update the handoff and report — do not run on to the 350k reminder and hand over code that was never run. Read files in parts, not whole; do not re-read what you have read; never dump large command output or full-size images into your context.
